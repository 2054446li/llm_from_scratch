# 饿了么物流管理 SOP 详细版（v2_detailed）

> **文档版本**: v2.0 详细版  
> **适用场景**: 饿了么物流全流程客服/运营处理  
> **更新日期**: 2026年8月

---

## Objective

1. **用户体验目标**: 确保用户从下单到收餐的全流程顺畅，订单准时送达率 ≥ 95%，平均配送时长 ≤ 30分钟
2. **商家运营目标**: 帮助商家高效处理订单，出餐时间控制在承诺范围内，商家接单率 ≥ 98%
3. **骑手服务目标**: 合理派单，保障骑手配送效率与安全，人均日单量 ≥ 35单
4. **平台质量目标**: 降低客诉率（< 0.5%），提升用户复购率和平台口碑

## Standard Operating Procedures

### 一、运单创建流程

#### 1.1 运单创建操作流程

```
┌─────────────────────────────────────────────────────────────────┐
│                     运单创建操作流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐  │
│  │ 1.接收订单│ -> │ 2.信息校验│ -> │ 3.生成运单│ -> │ 4.推送调度│  │
│  └──────────┘    └──────────┘    └──────────┘    └──────────┘  │
│                                                                 │
│  KCP: 订单信息完整性校验、地址有效性校验、配送范围校验           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

| 步骤 | 操作内容 | 注意事项 | Rule层约束 |
|------|----------|----------|------------|
| 1 | 接收订单系统推送的订单数据 | 校验订单来源合法性 | 仅接受已授权平台订单 |
| 2 | 校验订单信息完整性 | 核对地址、商品、金额等关键字段 | **KCP**: 地址精确到门牌号 |
| 3 | 生成唯一运单号 | 规则：日期+区域码+序列号 | 运单号全局唯一，不可重复 |
| 4 | 计算预计配送时长 | 基于距离、时段、天气等因子 | 恶劣天气自动延长预计时间 |
| 5 | 写入运单数据库 | 状态设为"待分配" | 关键节点必须记录时间戳 |
| 6 | 推送至调度系统 | 触发智能派单流程 | 5分钟内必须完成派单 |

### 二、运单状态流转流程

#### 2.1 状态流转图

```
待分配 → 已分配 → 骑手接单 → 到店取货 → 配送中 → 已送达 → 已完成
  │         │         │          │          │         │
  │         │         │          │          │         │
  └─────────┴─────────┴──────────┴──────────┴─────────┘
                    ↓ 异常分支
              已取消 / 异常处理中 / 已转单
```

#### 2.2 各阶段操作规范

| 状态 | 触发条件 | 操作内容 | KCP标记 | 话术示例 |
|------|----------|----------|---------|----------|
| 待分配 | 运单创建完成 | 进入派单池，等待调度 | 5分钟内必须完成派单 | "您的订单正在匹配骑手，请稍候" |
| 已分配 | 系统选定骑手 | 向骑手推送订单 | 派单响应时间≤30秒 | "已为您匹配到骑手，等待骑手确认" |
| 骑手接单 | 骑手点击接单 | 锁定运力，更新状态 | **KCP**: 接单时间戳记录 | "骑手已接单，正在赶往商家" |
| 到店取货 | 骑手到达商家 | 核对商品，确认取餐 | **KCP**: 到店时间、取餐时间记录 | "骑手已到店，正在取餐" |
| 配送中 | 骑手取餐完成 | 按导航路线配送 | GPS轨迹每10秒上报 | "骑手已取餐，正在配送中" |
| 已送达 | 骑手点击送达 | 确认送达位置和时间 | **KCP**: 送达时间确认 | "订单已送达，请确认收餐" |
| 已完成 | 用户确认/超时 | 订单闭环，触发结算 | 24小时内用户可申诉 | "订单已完成，感谢使用饿了么" |

```
┌─────────────────────────────────────────────────────────────────┐
│                    状态流转规则约束                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Rule 1: 状态流转合法性校验                                     │
│  - 状态变更必须符合预设流转图                                   │
│  - 非法状态变更自动拦截并告警                                   │
│                                                                 │
│  Rule 2: 时间戳完整性校验                                       │

│  - 超时未到店 → 自动预警并转派                                  │
```

### 三、调度系统流程

#### 3.1 智能派单逻辑

```
┌─────────────────────────────────────────────────────────────────┐
│                    智能派单系统算法逻辑                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  派单权重因子（按优先级排序）：                                  │
│                                                                 │
│  1. 骑手位置: 距离商家的直线/实际距离（权重40%）                │
│  2. 骑手负载: 当前已接订单数量（通常≤5单）（权重25%）           │
│  3. 配送方向: 订单目的地与骑手当前路线的匹配度（权重15%）       │
│  4. 预计时间: 基于历史数据的配送时长预测（权重10%）             │
│  5. 骑手评级: 服务评分、准时率等（权重5%）                      │
│  6. 天气路况: 实时天气、交通拥堵情况（权重5%）                  │
│                                                                 │
│  Rule: 恶劣天气自动延长预计送达时间，增加骑手补贴               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.2 派单流程

| 阶段 | 操作内容 | KCP标记 | Rule层约束 |
|------|----------|---------|------------|
| 订单入池 | 运单进入派单池 | 按区域、时效要求分组 | 派单半径不超过3公里 |
| 骑手筛选 | 筛选可用骑手 | 在线、空闲、区域内 | 骑手负载上限5单 |
| 匹配计算 | 计算匹配分数 | 综合距离、负载、顺路度 | 30秒内完成计算 |
| 订单推送 | 向最优骑手推送 | 等待骑手响应 | 接单响应时限30秒 |
| 响应处理 | 骑手接单/拒单/超时 | 更新运单状态 | 超时自动转派 |

#### 3.4 调度干预流程

| 干预类型 | 触发条件 | 操作流程 | 话术示例 |
|----------|----------|----------|----------|
| 人工调度 | 异常订单需重新分配 | 选择目标骑手 → 强制派单 → 通知双方 | "因特殊情况，您的订单已转派给其他骑手" |
| 爆单支援 | 区域运力不足 | 识别爆单区域 → 调派周边运力 → 启动众包 | "该区域订单较多，已加派骑手支援" |
| 订单转移 | 骑手突发情况 | 确认原因 → 释放运力 → 重新派单 | "骑手因车辆故障无法配送，已为您更换骑手" |
| 系统干预 | 超时风险订单 | 自动识别 → 提前转派 → 通知用户 | "系统检测到配送可能延迟，已优先安排其他骑手" |

### 四、骑手管理流程

#### 4.1 骑手入驻流程

| 阶段 | 操作内容 | KCP标记 | Rule层约束 |
|------|----------|---------|------------|

| 身份核验 | 实名认证 | **KCP**: 身份信息真实性 | 与公安系统联网核验 |
| 健康证审核 | 餐饮配送必需 | 健康证有效期校验 | 过期健康证无法接单 |
| 交通工具登记 | 电动车/摩托车登记 | 车辆信息备案 | 无牌车辆禁止接单 |

|------|------|--------|--------------|

#### 5.2 预警机制

| 预警类型 | 触发条件 | 预警级别 | 处理方式 |

### 六、异常处理流程

#### 6.1 异常分类与处理时效

| 异常类型 | 典型场景 | 处理时效 | KCP标记 |
|----------|----------|----------|---------|
| 订单异常 | 商品缺货、商家闭店 | 15分钟内 | **KCP**: 商家履约记录 |
| 配送异常 | 骑手无法联系、车辆故障 | 10分钟内 | **KCP**: 运力重新分配 |
| 地址异常 | 地址错误、用户不在家 | 15分钟内 | **KCP**: 用户确认 |
| 用户异常 | 用户拒收、要求退款 | 20分钟内 | **KCP**: 责任判定 |
| 系统异常 | 定位失败、APP崩溃 | 5分钟内 | **KCP**: 系统恢复 |

#### 6.2 异常处理流程

```
异常发现 → 异常定级 → 分配处理人 → 处理执行 → 结果确认 → 闭环归档
    │          │           │           │          │
    ▼          ▼           ▼           ▼          ▼
 系统自动    P0/P1/P2    骑手/客服    转派/退款   用户确认
 人工上报    分级响应    运营人员     补送等      满意度
```

#### 6.3 常见异常处理方案

**异常类型1: 骑手无法取货**
```
处理流程:
1. 联系商家确认备货情况
2. 商家未出餐 → 等待/申请延长取货时间
3. 商家已出餐但未找到 → 协助骑手与商家沟通
4. 超时可申请转派或取消
5. 记录商家履约情况

Rule: 商家出餐超时>30分钟，用户可申请全额退款
```

**异常类型2: 用户无法联系**
```
处理流程:
1. 骑手尝试3次电话联系（间隔2分钟）
2. 发送短信/APP推送通知
3. 等待10分钟
4. 按用户备注处理（放门口/前台）
5. 拍照留证 → 点击送达

Rule: 无接触配送订单，拍照后可直接放置
```

**异常类型3: 商品损坏/缺失**
```
处理流程:
1. 拍照取证
2. 联系用户协商处理
3. 必要时启动退款/补送流程
4. 责任判定（商家/骑手）
5. 追偿处理
```

## 附录：术语表

| 术语 | 说明 |
|------|------|
| 运单 | 物流配送任务的载体，包含订单、商家、用户、骑手等信息 |
| 骑手 | 负责商品配送的配送员 |
| 调度 | 将运单分配给合适骑手的过程 |

| 顺路度 | 订单与骑手当前路径的匹配程度 |
| 预派单 | 在商家出餐前提前分配骑手 |
| 闭环率 | 异常订单处理完成的比例 |

| P0/P1/P2 | 异常优先级，P0为最高优先级 |
