## 一、模型定位与规模（背景）

- **不是从零训练**：从 **DeepSeek-V2 的中间检查点**（已训 4.2T）出发，额外继续预训练 **6T tokens** → 总计接触 **10.2T tokens**。这是"在强通用底座上继续训代码"范式的延续（呼应 DeepSeek-Coder v1.5 的结论：强代码模型应建立在强通用 LLM 之上）。
- **MoE 架构**（沿用 DeepSeek-V2）：

| 模型 | 总参数 #TP | 激活参数 #AP | 预训练 Tokens | FIM |
|------|-----------|-------------|---------------|-----|
| DeepSeek-Coder-V2-Lite | 16B | 2.4B | 4.2T + 6T | 启用 |
| DeepSeek-Coder-V2 | 236B | 21B | 4.2T + 6T | 禁用 |

- **关键扩展**：编程语言 86→338；上下文 16K→128K（YaRN，scale=40, α=1, β=32，分两阶段 32K→128K 继训）。

> **后训练关联**：128K 长上下文对代码 RL 至关重要——rollout 常涉及长文件、多轮工具调用、长测试日志，上下文不足会直接限制可训练任务的复杂度。MoE 的小激活参数（21B/2.4B）则降低 RL rollout 的吞吐成本。

## 二、数据收集（预训练，§2）

### 数据配比
| 成分 | 占比 |
|------|------|
| 源代码 | 60% |
| 数学语料 | 10% |
| 自然语言 | 30%（直接采样自 DeepSeek-V2） |

### 代码数据来源（共 1,170B code-related tokens）
- **GitHub 过滤**（沿用 DeepSeek-Coder 规则）：平均行长>100 / 最大行长>1000 / 字母字符<25% / HTML 可见文本占比≥20% / JSON-YAML 限 50–5000 字符等 → 得 **821B 代码（338 语言）+ 185B 代码相关文本**。
- **CommonCrawl 召回**（沿用 DeepSeekMath 流程）：种子语料（StackOverflow/PyTorch 文档/StackExchange）→ 训 **fastText**（用 DeepSeek-V2 BPE 分词器，提升中文等召回）→ 域名占比>10% 判定相关 → 迭代 3 轮，得 **70B 代码 + 221B 数学** tokens；GitHub 再迭代 2 轮得 94B。

### 消融验证（表 1，1B 模型）
新代码语料 vs 旧语料：1T 时 HumanEval 30.5%→36.0%、MBPP 44.6%→49.0%；2T 时进一步到 **37.2% / 54.0%**。→ 新语料更优。

> **后训练关联**：① "种子 + fastText 召回 + 迭代扩种子"与后训练构造高质 SFT/偏好数据的提纯思路同构；② 60/10/30 配比是上游约束——后训练只能在基座能力上对齐微调，无法凭空补足某类能力。

## 三、训练策略（§3）

### 3.1 训练目标
- **16B**：Next-Token-Prediction + **FIM**（PSM 模式，0.5 比例，文档级）
  ```
  <｜fim_begin｜>f_pre<｜fim_hole｜>f_suf<｜fim_end｜>f_middle<|eos_token|>
  ```
- **236B**：**仅 Next-Token-Prediction**（大模型已能涌现补全能力，FIM 会牺牲生成质量——目标与能力的权衡）。

### 3.2 架构与稳定性
- 对齐 DeepSeek-V2。训练遇**梯度尖峰不稳定**，归因于**指数归一化技术**，**回退到常规归一化**解决。

### 3.3 超参
AdamW（β₁=0.9, β₂=0.95, wd=0.1）；余弦衰减，2000 warmup，末段降至初始 10%。

### 3.4 长上下文
YaRN 扩到 128K；两阶段继训（32K×1000步 + 128K×1000步），上采样长上下文数据；NIAH "大海捞针"全长 128K 通过。

## 四、对齐阶段（§3.5）★ 后训练核心

### 3.5.1 监督微调（SFT）
- 数据：DeepSeek-Coder/Math 的 **20k 代码 + 30k 数学**指令，外加从 DeepSeek-V2 采样的**通用指令** → 共 **300M tokens**。
- 训练：余弦调度，100 warmup，lr **5e⁻⁶**，batch 1M tokens，总 **1B tokens**。

> **要点**：① 混入通用数据是为防专项微调导致的**通用能力退化（catastrophic forgetting）**——最终 MMLU 79.2%、MT-bench 8.77 几乎不掉即证；② SFT 量极小（1B vs 预训 10.2T），说明对齐只"激发"不"注入"能力。

### 3.5.2 强化学习（RL）

**(1) Prompts**：从多源收集代码+数学 prompt，**每条代码 prompt 自带 test cases**，过滤后约 **40k 条**。

**(2) Reward Modeling（奖励建模）——本文最值得深究的决策**
- 数学偏好：用 **ground-truth 标签**。
- 代码偏好：编译器虽能给 **0/1 反馈**（是否过全部测试），但**测试覆盖不全 → 0/1 有噪声、有偏、次优**。因此**在编译器数据上训练一个奖励模型（RM）**，用 RM 在 RL 中提供信号，**比原始编译器信号更鲁棒、泛化更好**。
- 经验证据（图 3，LeetCode / LeetCode-zh）：**RM 信号曲线明显高于 compiler 信号**；故后续全用 RM 信号。

> **为什么 RM 能反超它学习的编译器标签？**（论文留白，推断）
> 这是一个**结果奖励模型（Outcome Reward Model, ORM）**，标签来源是"执行反馈"而非人工偏好。RM 不是复现标签，而是做低方差估计器，三机制叠加：
> 1. **去噪**：见全数据集 + 容量有限 → 拟合不了单点噪声，对"错但碰巧过弱测试"的解给中间分而非满分 → 抑制 **reward hacking**；
> 2. **稠密化**：0/1 稀疏，RM 给连续分 → credit assignment 更细，RL 更稳；
> 3. **解耦执行**：RM 一次前向出分，便宜，且能给"无测试/测试薄弱"的 prompt 打分。
> 一句话：**编译器给"在这几个测试点上对不对"，RM 学"代码看起来对不对"**——平滑、去噪、可外推的近似。
> 路线定位：介于 **RLVR（直接用可验证 0/1，简单无偏但稀疏易 hack）** 与**经典 RLHF RM（人标偏好，稠密但贵）**之间的折中——"有可验证奖励 ≠ 该直接拿来当 reward；验证不完备时，学一个平滑代理更优"。

**(3) RL 算法：GRPO**（Group Relative Policy Optimization，同 DeepSeek-V2）
- 相比 PPO **无需 critic/value 网络**，成本更低。
- 机制：同一 prompt 采**一组（group）**输出，用组内奖励均值作基线，优势 ≈ (自身奖励 − 组均值)/组标准差。
- 优点：省掉与策略同规模的 value 网络，对 **236B MoE 的 RL 吞吐**至关重要；缺点：方差估计依赖组大小，组太小不稳。

### FIM 与对齐的兼容
16B 在对齐时仍用 FIM 微调，**避免对齐破坏代码补全能力**——"对齐别把基础能力训没了"。

## 五、关键实验结果（§4，节选）

### 代码生成（表 3，HumanEval/MBPP⁺ 多语言平均）
| 模型 | #TP/#AP | HumanEval(Py) | MBPP⁺ | 平均 |
|------|---------|---------------|-------|------|
| GPT-4o-0513 | - | **91.0%** | 73.5% | **76.4%** |
| **DS-Coder-V2-Instruct** | 236B/21B | **90.2%** | **76.2%** | **75.3%** |
| GPT-4-Turbo-0409 | - | 88.2% | 72.2% | 72.5% |
| DS-Coder-V2-Lite-Instruct | 16B/2.4B | 81.1% | 68.8% | 65.6% |
| DS-Coder-instruct | 33B | 79.3% | 70.1% | 61.9% |

→ 平均第二，仅次 GPT-4o，**打破闭源主导**；Java/PHP 最高分。**Lite-16B（激活 2.4B）超 33B**（65.6% vs 61.9%）。

### 竞赛编程（表 4，防污染）
| 模型 | LiveCodeBench 总体 | USACO |
|------|---------------------|-------|
| GPT-4-Turbo-0409 | **45.7%** | 12.3% |
| GPT-4o-0513 | 43.4% | **18.8%** |
| **DS-Coder-V2-Instruct** | **43.4%** | 12.1% |

→ 与 GPT-4o 并列大模型最高，整体第二。

### 代码补全（Lite，激活仅 2.4B）
- **RepoBench v1.1**（表 5，仅用 2023.12 防泄漏）：Python 38.9% / Java 43.3%，达 DS-Coder-Base 33B（Py）、7B（Java）水平。
- **单行 FIM**（表 6）：平均 **86.4%**（Py 80.0 / Java 89.1 / JS 87.2），与 33B 持平居首。

### 代码修复（§4.3）
用 Defects4J（仅取 238 个单方法 bug）、SWE-bench、Aider。DeepSeek-Coder-V2 是**首个 SWEBench >10% 的开源模型**。

### 数学与通用
- MATH **75.7%**（逼近 GPT-4o 76.6%）、GSM8K 94.9%、AIME 2024 超闭源；
- MMLU 79.2% / arena-hard 65.0 / MT-bench 8.77 / alignbench 7.84——通用能力几乎不退化。

## 六、相比 DeepSeek-Coder (v1) 的改进 ★

**最大改进（一句话）**：训练范式从"**纯代码从零训练 + 仅 SFT**"跃迁到"**在强通用 MoE 底座上继续预训练 + 真正的 RL 对齐**"——这让开源模型**首次在代码+数学上反超闭源 SOTA**（v1 当时只能超 GPT-3.5-Turbo、追不上 GPT-4）。

| 维度 | DeepSeek-Coder (v1) | DeepSeek-Coder-V2 | 改进意义 |
|------|---------------------|-------------------|----------|
| **训练起点** | Dense，**从零训练 2T** | MoE，**从 DeepSeek-V2 中间检查点继续训 6T**（共 10.2T） | 站在强通用底座上，代码/数学/通用三者兼得 |
| **架构** | Dense 1.3/6.7/33B | **MoE** 16B(激活 2.4B) / 236B(激活 21B) | 激活参数小 → 推理 / RL rollout 吞吐高 |
| **对齐管线** | 仅 **SFT**（指令微调） | **SFT + GRPO 强化学习 + 奖励模型** | ← 后训练视角下最本质的改进 |
| 数据配比 | 87% 代码 / 13% NL | 60% 代码 / 10% 数学 / 30% NL | 显式加重数学，平衡通用能力 |
| 语言 / 上下文 | 86 语言 / 16K | **338 语言 / 128K** | 覆盖面与长任务能力（量的扩展） |
| 代表性能 | HumanEval 50.3(base)/69.2(instruct)，超 GPT-3.5 | **HumanEval 90.2 / MATH 75.7**，比肩 / 反超 GPT-4o | 打破闭源壁垒 |

**从后训练方向看，最大改进 = v1 没有 RL，v2 引入了完整 RL 对齐**：
- v1 的对齐止步于 SFT，能力全靠高质量预训练数据 + 指令微调，无偏好优化 / 无 RM / 无 RL。
- v2 在 SFT 之上叠加：**GRPO**（去 critic，省显存，适配大 MoE）+ **编译器反馈训练的奖励模型**（而非直接用 0/1，解决测试覆盖不全的噪声与 reward hacking）+ 数学侧 ground-truth 奖励。
- 一句话：**v1 证明"高质量数据 + SFT"能造强开源代码模型；v2 证明"在此之上叠加可验证奖励的 RL"能把开源推过闭源 SOTA 那条线**。RL 对齐是跨越闭源壁垒的临门一脚。

> **常见误区**：表面最显眼的是"语言 86→338、上下文 16K→128K"，但这些是**量的扩展**；真正质变的是**训练范式（强底座继续训 + RL 对齐）**——前者扩大适用面，后者才是性能反超闭源的根本原因。

## 一句话总结

DeepSeek-Coder-V2 通过**在 DeepSeek-V2 强底座上继续预训练 6T tokens**（语言 86→338、上下文 16K→128K），并在对齐阶段用 **SFT + GRPO** 加上**用编译器反馈训练的奖励模型**（而非直接用 0/1），训出首个在代码+数学上**反超闭源 SOTA 的开源 MoE 模型**（236B/激活 21B），核心后训练命题是"**可验证执行信号 + 平滑化奖励模型 + 去 critic 的 GRPO = 高效稳健的代码 RL**"。

---

## 对后训练工程师的关键启示

1. **可验证奖励 ≠ 直接用规则奖励**：测试覆盖不全时，0/1 信号有偏且易被 reward hacking；**训一个 RM 做平滑/去噪代理**反而更鲁棒（图 3 实证）。这是 RLVR 与 RLHF 之间的实用折中。
2. **GRPO 省 critic**：去掉与策略同规模的 value 网络，用组内相对优势，对大 MoE 的 RL 吞吐是关键杠杆——后训练面试高频考点（务必能对比 PPO）。
3. **SFT 配比防遗忘**：专项数据激发 + 通用数据保底，量小只为激发能力；通用基准不掉是配比成功的标志。
4. **对齐别毁基础能力**：16B 对齐期保留 FIM，防补全能力被对齐冲掉。
5. **强底座优先**：从通用强模型继续训，而非从零——后训练效果上限由基座决定。
6. **长上下文服务于 RL**：128K 不只为推理，也为支撑更复杂的代码 rollout。
